## 1. Project Overview

The AI Shopping Assistant is an agentic system that accepts a natural language query,
searches products across multiple mock e-commerce stores, scores and ranks results,
and returns a plain English recommendation powered by an LLM.

It is an open source learning project for interns at Data Science Academy,
built in 4 progressive phases. Each phase is independently deployable and testable.

**Note:** the project scope was changed from an earlier skincare-recommendation
concept to a multi-store **smartphone** shopping assistant. All example queries,
README examples, and product data now use phones (e.g. "Best Samsung phone under
₹30,000") — do not reintroduce skincare examples anywhere in docs or tests.

**Current status:**
- Phase 1 — Complete. Static CSV pipeline, 3 agents, FastAPI /chat endpoint, full test suite.
- Phase 2 — In Progress. Live WooCommerce REST API across 2 active stores (Store A: Amazon, Store B: Flipkart). Store C pending data.
- Phase 3 — Planned. LangGraph ReAct loop, Redis short-term memory, PostgreSQL long-term preferences.
- Phase 4 — Planned. LangSmith/Langfuse tracing, Guardrails AI safety layer, MCP server wrapping.

## 3. Build / Test / Run Commands

```bash
# Install dependencies
pip install -r requirements.txt
pip install google-genai          # or: openai / anthropic

# Copy env template — you'll fill in your own WooCommerce keys after Step below
cp .env.example .env

# Install and verify pre-commit hooks — required immediately after cloning

# Set up your own local WooCommerce store — required for every intern, not

# Clean and load product data into your own store once WooCommerce is installed
# and your WC_CONSUMER_KEY/WC_CONSUMER_SECRET are in .env
python data/clean_products.py
python data/load_products.py --store A --clear
python data/load_products.py --store B --clear

# Start the API server
uvicorn backend.main:app --reload

# API docs (interactive)
# http://localhost:8000/docs

# Test a query manually (requires server running)
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "good phone under 15000"}'
```

## 4. Code Style and Conventions

### General
- Python 3.10+ required.
- Follow PEP 8. Use type hints on all function arguments and return values.
- Every function must have a docstring (Args, Returns, Example where applicable).
- Keep functions under 40 lines. Split if longer.
- No hardcoded API keys, URLs, or passwords anywhere in source files — always use .env.

### LLM Provider — Provider-Agnostic Design

The system supports Gemini, OpenAI, and Anthropic. `LLM_PROVIDER` in `.env` controls
which is active. When adding LLM calls, always route through the provider pattern:

```python
provider = config.LLM_PROVIDER.lower()
if provider == "gemini":
    return _call_gemini(prompt)
elif provider == "openai":
    return _call_openai(prompt)
elif provider == "anthropic":
    return _call_anthropic(prompt)
```

Never hardcode a specific provider. New provider integrations go in
`agents/recommend.py` as `_call_<provider>()` stubs following the existing pattern.

Until an LLM is implemented, `get_recommendation()` returns a clearly-labeled
placeholder response instead of crashing — this keeps the pipeline testable
end-to-end without requiring the LLM task to be complete first.

### Category-Aware Spec Pattern

When adding scoring logic for a new product category:
1. Add a new profile to `data/spec_profiles.py` under `SPEC_PROFILES`
2. Add a new scorer function in `agents/compare.py` (e.g. `score_laptop_specs()`)
3. Add a routing `elif` in `score_specs()` in `agents/compare.py`
4. Add a processor function in `data/clean_products.py` (e.g. `process_laptops()`)

Never hardcode category logic directly inside `agents/compare.py` outside the
`score_specs()` routing function. Keep category logic modular and extensible.

### WooCommerce Store Pattern

`agents/search.py` queries live stores first, falls back to CSV automatically
if no store is reachable or no API keys are configured. When adding Store C:

```python
# In agents/search.py — load_products_from_woocommerce()
if config.STORE_C_CONSUMER_KEY and config.STORE_C_CONSUMER_SECRET:
    stores.append((config.STORE_C_URL, config.STORE_C_CONSUMER_KEY,
                   config.STORE_C_CONSUMER_SECRET))
```

Always use the conditional key-check pattern — never hardcode a store URL
or assume a store is available.

### Deduplication Rule

`data/clean_products.py` deduplicates on `(product_name, brand, store, price)` —
not just `(product_name, brand, store)`. This is deliberate: after name cleaning
strips colour/RAM/storage variants from the display name, products that look
identical by name can still be genuinely distinct at different price points.
Do not simplify the dedup key back to 3 fields.

## 6. Contribution Rules

### Branch Naming
```
internname/feature-name
```
Examples: `priya/gemini-integration`, `rahul/fuzzy-search`, `nandana/flipkart-scraper`

### Commit Message Format
```
type: short description (under 72 chars)

Optional longer body explaining why, not what.

Signed-off-by: Your Name <your.email@example.com>
```

Types: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`

The `Signed-off-by` line is required on every commit (DCO sign-off).
Add it automatically with: `git commit -s -m "feat: your message"`

### Submission Workflow — Before You Commit

Committing and pushing is the *last* step, not the first, after finishing a task:

1. Complete the assigned feature and run `pytest tests/ -v` — fix anything broken.
2. Record a demo video (max 3 minutes): feature implementation, code walkthrough,
   running the app, running pytest, and expected output.
3. Upload the video to your personal Google Drive folder `DSA_OpenSource_<YourName>`.
4. Share that folder with `varsha.dsa2024@gmail.com` (Viewer permission).
5. Name the video `Week_<WeekNumber>_Task_<TaskNumber>_<FeatureName>_<YourName>.mp4`.
6. Post the Drive link in Discord and tag the mentor.
7. Only after mentor approval: commit (with sign-off) and push.

An AI assistant should remind the contributor of this sequence rather than
generating a `git commit`/`git push` as the immediate next step after code changes.

### PR Requirements
- All tests must pass: `pytest tests/ -v`
- No `.env` file committed (verify with `git status` before pushing)
- No `data/raw/*.csv` files committed (add to `.gitignore` if missing)
- Mentor approval received on the demo video (see Submission Workflow above)
- PR description must state what was changed and why
- Tag Varsha or Nandana as reviewer

## 8. Store Configuration

Per Minu: WooCommerce stores are **not centrally hosted** — each intern installs
Docker and stands up their own local WooCommerce instance from scratch (see
`README.md` for the full step-by-step: Docker Desktop → `docker compose up -d`
→ WordPress install → WooCommerce install → generate your own API keys → load
data with `data/load_products.py`). The table below describes the intended
per-machine layout, not a shared server — "active" means "you've completed the
setup and loaded data for it on your own machine," not "already running for you."

| Store | Database | WordPress | WP-CLI | URL (on your machine) | Status |
|---|---|---|---|---|---|
| Store A | `db` | `wordpress` | `wpcli` | http://localhost:8080 | Set up first — data loaded via `load_products.py --store A` |
| Store B | `db_b` | `wordpress_b` | `wpcli_b` | http://localhost:8081 | Same process, second container set |
| Store C | `db_c` | `wordpress_c` | `wpcli_c` | http://localhost:8082 | Container only — no data until Nandana's scrape lands |

Store A and B keys are in `.env` as `WC_CONSUMER_KEY`/`WC_CONSUMER_SECRET` and
`STORE_B_CONSUMER_KEY`/`STORE_B_CONSUMER_SECRET`. Store C keys are placeholders
until data is loaded. Do not query Store C until its keys are real values.

Each store needs the permalink fix and the Basic Auth fix applied as part of
its own setup (see `README.md` Section 6 for the full sequence per store) —
these are no longer pre-applied on a shared server, so don't skip them:

```bash
# Permalink fix (run against the store's own wpcli service, e.g. wpcli or wpcli_b)
docker compose run --rm wpcli rewrite structure '/%postname%/' --hard --allow-root
docker compose run --rm wpcli rewrite flush --hard --allow-root

# Basic Auth fix (run against the store's own wordpress container, e.g. wordpress or wordpress_b)
MSYS_NO_PATHCONV=1 docker compose exec -T wordpress mkdir -p /var/www/html/wp-content/mu-plugins
MSYS_NO_PATHCONV=1 docker compose exec -T wordpress bash -c "cat > /var/www/html/wp-content/mu-plugins/enable-basic-auth.php << 'EOF'
<?php
add_filter( 'woocommerce_rest_is_request_to_rest_api', function() { return true; } );
add_filter( 'woocommerce_rest_check_permissions', function( \$permission, \$context, \$object_id, \$post_type ) {
    return true;
}, 10, 4 );
EOF"
docker compose restart wordpress
```

Apply the same pair of fixes to Store C (swap in `wpcli_c`/`wordpress_c`) once its data is loaded.

## 10. Known Infrastructure Notes

These are hard-won fixes that must not be undone:

**Apache Authorization header stripping (Store A, B, C)**
WooCommerce REST API on plain HTTP rejects Basic Auth by default. Fixed via a
must-use PHP plugin at `/var/www/html/wp-content/mu-plugins/enable-basic-auth.php`.
Now that each intern sets up their own stores from scratch (Section 8), this is
no longer pre-applied on a shared server — every intern applies it themselves
to their own `wordpress` and `wordpress_b` containers as part of setup, and
again to `wordpress_c` once Store C's data is loaded.

**Git Bash path mangling on Windows**
When running `docker compose exec` with Unix paths, prefix with `MSYS_NO_PATHCONV=1`
to prevent Git Bash from converting `/var/www/html` to a Windows path. Without this,
any `exec` command touching a container path will silently fail on Windows.

**Windows terminal encoding**
If `clean_products.py` crashes on the arrow character, run:
```bash
export PYTHONIOENCODING=utf-8
```
This is a one-time fix per terminal session on Windows.

**Permalink fix (required after every fresh WordPress install)**
After installing WordPress and WooCommerce, always run:
```bash
docker compose run --rm wpcli rewrite structure '/%postname%/' --hard --allow-root
docker compose run --rm wpcli rewrite flush --hard --allow-root
```
Without this, `/wp-json/` returns HTML instead of JSON.
